## 1. P0：知识库作业权限闭环

### 1.1 改了什么

| 位置 | 变化 |
|---|---|
| `api/knowledge.py`（上传/导入） | 提交**之前**先 `claim_owner`（失败即 409），提交成功后再补文档级 ACL。旧顺序是"先提交再 claim"，claim 失败时路由已返回 202，上传者立刻在自己的列表/详情里看不到刚上传的文档 |
| `knowledge_store.py` | 抽出唯一可见性谓词 `_owner_acl_visible(owner, acl_principals, principal_id, mode)`；`visible_documents` 改为调用它（行为不变）。`list_documents` / `list_jobs` 新增 keyword-only `principal_id`；过滤发生在 `status`、`cursor`、`limit` **之前**，`next_cursor` 由过滤后页尾编码。新增 `job_document_id` / `document_visible_to` |
| `api/knowledge.py` | `list_jobs` / `get_job` / `retry_job` 解析 `X-API-Key`；单条作业不可见统一 **404**（不是 403，避免存在性 oracle）；`retry` 在**创建新作业之前**完成鉴权，因此鉴权通过后才可能出现 409 状态错误 |

为什么不直接用 `visible_documents` 过滤列表：它要求 active revision 与有效期，会把
pending/failed/过期文档从**管理视图**里藏掉（`test_knowledge_api.py` 的失败文档可见断言会直接红）。

### 1.2 直接验收（单测，`tests/test_knowledge_jobs_acl.py`，6 例）

### 1.2b 复核发现的四条越权面（本轮已修）

对抗复核（六个维度 + 逐条反驳）在知识库权限上找出四条真实越权，均已修复并加测试：

| 越权 | 触发 | 修复 |
|---|---|---|
| 只读 ACL 成员能改/删文档 | 文档"有 ACL、无 owner"时，`_enforce_document` 只看 owner 侧表 → `acl.authorize` 按"未记录 owner 就放行"处理 → 陌生 principal 可 `activate`、`delete` | 读写拆开：读用 `document_visible_to`，写用 `document_writable_by`（**owner 优先**，只有确实没有 owner 才认 ACL 成员）；读路由不可见统一 404，写路由保留 403 |

## 4. P0：拆开诊断 run 与聊天流 run

### 4.1 缺陷（比"文件名混用"更严重）

请求体 `run_id` 既是"追问引用的诊断 run"又被当作聊天事件文件名与 `event_id` 前缀。
同一诊断 run 追问两次 → 写同一个文件、`seq` 都从 1、`event_id` 前缀相同 →
`read_after` 按 `event_id` 去重把第二次的事件**静默丢弃**。

### 4.2 改法

- 每次 `/api/chat_stream`（以及非流式 `/api/chat`）生成独立 `chat_run_id = uuid4().hex`，
  作为 SSE 的 `run_id`/`event_id` 前缀与事件文件名；请求里的 `run_id` **只**传给
  `_load_context_async`；
- `chat_events.append/record` 新增 `session_id` 关键字参数（显式传入时覆盖事件里的值），
  `chat.py` 一律传 `request.id`；
- `read_after` 新增 `session_id` 参数：给了就要求每条待返回记录的 `session_id` 一致，
  否则抛 `ChatStreamNotFound`（路由 404）；会话校验**先于游标与去重**——若放在
  `after_seq` 之后，同一个已知 run 会按游标位置给出"空页"或"404"两种结论，等于
  把"记录存在但对我不可见"变成可探测；
- dev 模式缺 `session_id` 的既有放行**保持不变**（G6 只要求不同 session 不能借已知 run 读）。

### 4.3 直接验收（容器内真实 HTTP）

```
# 同一诊断 run（'a'*32）连续追问两次
stream1: run_id=7bcf7ef1… events=6 seq=1..6 last=done/answered session=g6-run-split
stream2: run_id=16bfddc2… events=7  seq=1..7 last=done/answered session=g6-run-split
两个 chat run 不同；都不等于请求 run_id
# 落盘
7bcf7ef1….jsonl: lines 6 seq [1..6] session {'g6-run-split'}
16bfddc2….jsonl: lines 7 seq [1..7] session {'g6-run-split'}
# 续读
GET /api/chat/events/<own run>?session_id=g6-run-split   -> 200, 6 条, truncated=false
GET /api/chat/events/<own run>?session_id=g5-container-cite -> 403（会话归属不符）
```

单测侧另有：跨 session 续读 404 且原文件字节数/行数不变；`purge_expired` 能删过期文件；
`append` 的显式 session 覆盖；缺 `session_id` 字段的旧记录按不匹配处理。

## 5. P1：聊天流生命周期的三个确定问题

| 问题 | 处理 |
|---|---|
| `purge_expired()` 没有调用点 | 接入既有清理入口：`app/main.py` 的 lifespan 在 trace retention 之后调用一次；不新增后台线程。模块文档改写为"启动时调用一次，另有 `purge_expired()` 供运维显式调用" |
| `fetch/read` 网络异常且已有 `run_id` | `web/src/chat.ts` 的 catch 分支改为走与 EOF **完全相同**的 `settleResume`（`MAX_RESUME_ATTEMPTS=2` 有界）；没有 `run_id` 才直接报错 |
| 主动"停止"被当成待恢复流 | `ChatPanel` 的停止按钮 abort 后 `writePendingStream(storage, null)`，清掉 `CHAT_PENDING_KEY` |
| 多标签页 | 明确写成"同一浏览器只支持一个活动聊天标签页；多标签页共享 `oncall.chat.pending`，后发的流覆盖续读位置"，同时写进 ChatPanel 说明文案与 README「当前限制」。**不做**跨标签页同步层 |

前端测试：74 通过（新增"网络异常后按 run_id 续读拿到终态"、"首个续读请求 502 后仍重试成功"、"abort 后不再发续读请求"、"会话 ID 输入被收敛而非静默丢弃"）。

取舍如实记录：停止后清 pending 意味着**该次已落盘事件的续读位置丢失**。服务端只在收到
`done` 时才 `append_turn`，所以如果停止发生在生成过程中，刷新后既没有历史回答也不能续读——
那次主动取消的回答整体消失。这是"不要误把主动取消当成待恢复流"的代价，不是附带收益。

## 6. P1：诊断路径使用同一 principal 的 RAG 可见性

- `knowledge_wiring.need_principal_scope(principal_id)`：判据只有一条——**拿到 principal 就启用**

  能在诊断里当证据。那是真实的越权面，已修正；
- `local_only_retriever(principal_id=..., filters=...)` 仍用
  `create_local_vector_store_manager()`（A03 的本地 embedding 约束不变），principal/filters
  只在拿到身份时下传；
- `knowledge_tools(execution_mode=..., principal_id=...)`：非 local 分支在拿到 principal 时
  构造显式 `VectorStoreRetriever`，只有空 principal 才保持 `retriever=None`；
- owner 传播链：`api/aiops.py` → `aiops_service.diagnose` → `run_diagnostic` →
  `run_local` / `run_cloud_multi` → `create_tools_compat` → `create_run_tools` →
  `knowledge_tools`。`create_tools_compat` 用既有 `_accepts_keyword` 裁剪，旧 3 参替身不炸。

**注意 dev 模式的实际变化**：dev 单租户下诊断现在也按 `visible_documents` 过滤（有效期、
ACL、owner）。这是刻意的：同一个人不该在两条路径上看到不同集合。它意味着带
`valid_from/valid_until` 的文档在诊断里也开始遵守有效期——不再是"诊断全量、问答受限"。

直接验收（`tests/test_diagnosis_knowledge_principal.py`，8 例）：

- multi 模式下 A 的私有文档：A 的诊断检索器与 A 的 `/api/chat` 检索器**逐条结果相同**；
  B 的两条路径都看不到 A 的文档，反之亦然；
- single 模式下无 owner 文档在两条路径都仍可见，且结果逐条相同；
- `create_run_tools(owner=…)` 把 principal 传进 `knowledge_tools`；`run_local` 转发 owner；
- 本地模式带 principal 时仍是 `LocalOnlyEmbeddings` 且 `_store is not` 全局 manager。

**边界**：旧路径 `app/tools/knowledge_tool.py`（`retrieve_knowledge` 的 LangChain 版）与

这两个入口当前**未被双模式诊断使用**，但仍挂在 `app/tools/__init__` 上，属已知缺口。

## 9. 仍未验证 / 未做（不得写成已完成）

1. **SSH 只读 staging**：无获授权主机，未执行，不伪造。
2. **CUDA torch、PyMilvus ORM 迁移、GitHub CI 实跑、Linux `flock` 分支、真实 IME/读屏器**：
   按任务书留作独立任务，本轮未碰。
3. **真实 TCP 断线**：本轮验证的是"客户端截断 / 网络异常后按 seq 续读"，不是"TCP 断开时
   后端仍持续执行"。后者需要能在链路上直接杀连接的环境。
4. **旧知识工具路径**：`app/tools/knowledge_tool.py` 与 `rag_agent_service.py` 仍无 principal。
5. **多 key 端到端**：进程只支持一个生效 `API_KEY`，所以"多租户"只能在测试里用不同
   `principal_id` 构造，不是多用户账号体系。
6. **`by_category` 桶**：运行时没有题目分类器，仍只能诊断用。
7. **镜像仍是 10.7 GB**：`nvidia`/`torch`/`triton` 仍占大头；CPU 版 torch 配方已验证但未落地。
8. **本机 apt 源不稳定**：`deb.debian.org` 在本机被边缘节点大量 502（同一 URL 用 `curl/8.5.0`
   UA 可 200、apt 默认 UA 502，且 security/updates 两个 suite 尤其严重）。因此本轮镜像用
   一个**只改 apt 步骤**的本地 Dockerfile 变体构建；仓库 `Dockerfile` 未改，CI 上的
   `--pull --no-cache` 也仍未在 GitHub 上真实跑过。

## 10. 这轮可以怎么写 / 不能怎么写

**可以写**（都有产物与分母）：

- 知识库作业的 principal 边界：列表/详情/重试都按文档可见性判定，单条不可见统一 404，
  retry 在创建新作业前鉴权；隐藏文档不再消耗分页 `limit`。容器内用另一把 key 复验
  （列表为空、详情 404、retry 404 且作业数不变）。
- 诊断 run 与聊天流 run 拆分：同一诊断 run 连续追问得到两个独立 chat run，两个事件文件
  `seq` 都从 1 连续；跨 session 续读 404 且原文件不变。
- 聊天流生命周期：启动清理过期事件、网络异常走有界续读、主动停止清待续读位置、
  单活动标签页限制写进界面与 README。
- `AUTH_MODE=deployment` + key 的 401/200 实测；`rag=ready` 与 `liveness=healthy` 分开报告。
- 评测快照一致性校验接进 `eval_generation`：profile 与当前题集/manifest/descriptor/store
  对不上就停止（真实产物 0 差异）。

**不能写**：

- "支持多用户/多租户账号体系"——单 API Key、文档级 ACL，没有用户表。
- "诊断路径已全部接入 principal"——旧 LangChain 工具路径仍未接。
- "验证了真实断线恢复"——只验证了客户端截断/网络异常后的续读。
- "CI 镜像构建通过"——GitHub Actions 的 docker job 从未真实执行。
- "镜像已去掉 CUDA torch"——仍是 10.7 GB。
- 任何"问答准确率 X%"——三层指标各自分母，没有合成口径。
