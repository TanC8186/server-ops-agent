## 1. P0-1：上传归属与文档提交的一致性

### 1.1 已确认的缺陷（本轮实测复现）

| 缺陷 | 复现结果 |
|---|---|
| metadata 校验晚于 owner 写入 | `valid_from=not-a-date` → **400**，`store.documents` 为空、`store.json` 都没创建，但 **ACL 侧表已有 `knowledge_document:<doc_id>`** → 幽灵 owner。此后同名上传被**永久 409**，且 `DELETE` 因 `has_document=False` 返回 404，`record_owner("")` 那行永远执行不到，**API 层无法自愈** |
| 失败上传把共享文档私有化 | 对"已存在的无 owner 共享文档"发一次非法 metadata 的请求：400，正文没动，但 owner 已被占 → BOB 由可见变不可见 |
| ACL seal 失败 → 上传者失明 | `acl_principals=[别人]` + `add_acl_principal` 抛异常 → 仍 **202**；随后 `list_documents` 不含、`get_job` 404、`list_jobs` 不含、检索为空、`delete/activate` 403、`revisions/retry` 404，而 `document_writable_by` 却是 **True**（可见性一失败，owner 的写权限根本没机会生效） |

根因是**双层抑制**：`_owner_acl_visible` 在 `members` 非空时短路忽略 owner；同时四个调用点都先做 `owner = None if members else ...`。**只改谓词无效**——实测 `visible_to` 仍为 False。

### 1.2 改法

| 位置 | 变化 |
|---|---|
| `api/knowledge.py` 上传/导入 | 顺序改为：文件名 → 内容 → **`normalize_document_metadata`** → 同名文档写权限 → `document_id_for` → **claim（记录 `owner_before`）** → `submit_document` → `_seal_uploaded_document` |
| `api/knowledge.py` 回滚 | 提交抛异常时调 `_release_uncommitted_owner`：**只在 `owner_before is None`（本次新建）时**回滚 |
| `core/principal.py` | 新增 `release_owner_if(kind, id, principal)`：**条件删除**，只有当前 owner 仍是该 principal 才删 |
| `knowledge_store.py` | 谓词改为 **`owner OR ACL`**；四个调用点（`document_visible_to` / `list_jobs` / `list_documents` / `visible_documents`）**无条件**读 owner |
| `api/knowledge.py` seal | 返回 `bool`；失败时响应带 `acl_sealed=false`，不把部分成功包装成完全成功 |

为什么不用无条件删除回滚：同一 principal 的并发上传会派生同一个 `document_id`（`document_id_for(source_uri)`），两方都读到 `owner_before=None`、都 claim 成功，谁失败谁裸删就会抹掉对方刚写下的记录。条件删除把窗口关掉。

### 1.3 直接验收（`tests/test_knowledge_upload_consistency.py`，11 例）

| 场景 | 断言（验证**存储状态**，不只是 HTTP 码） |
|---|---|
| 非法 `valid_from` / `valid_until` / `acl_principals`（参数化 3 例） | 400；`documents == {}`；**ACL 侧表 0 条 doc owner**；随后同名合法上传 202 |
| `valid_from > valid_until` | 400；无 owner 记录 |
| 失败上传不得私有化共享文档 | 400 后 BOB 仍可见；owner 仍为 `None` |
| 提交失败回滚本次新建 owner | 500；**doc owner 记录 0 条**；同名重传 202 |
| 提交失败不动已有 owner | 500；owner 仍是 DEV |
| 条件删除而非盲删 | 对别人的记录 `release_owner_if` 返回 False 且不删除；本人可删 |
| ACL seal 失败仍可用 | 202 且 `acl_sealed=false`；上传者 `visible_to`/`list_documents`/`get_job`/`visible_documents` 全部可见；被显式共享者可见；第三方不可见 |
| seal 成功 | 响应不含 `acl_sealed`；ACL 含 uploader |

## 4. P1-2：镜像构建 provenance 与 Compose 验收

### 4.1 标准 Dockerfile 构建（本轮真实完成）

G6 曾因本机 apt 502 用临时 `.g6-local.Dockerfile` + `--network host` 构建，本轮**用仓库原始 `Dockerfile` 完成了构建**，临时变体不再参与：

```
命令：DOCKER_BUILDKIT=0 docker build --no-cache \
        --build-arg GIT_REVISION=b27f9f4… \
        --build-arg HTTP_PROXY=http://host.docker.internal:7897 \
        --build-arg HTTPS_PROXY=http://host.docker.internal:7897 \
        -t oncall-agent:g7-standard-20261029-024455 .
结果：Successfully built 19b5710e2cfd，30 步，10 681 408 761 B
```

为什么需要 build-arg 代理：本机 `files.pythonhosted.org` 直连超时（实测 21.7 s 无响应），apt 在 host 网络下已恢复但 PyPI 大包（transformers / nvidia-cusolver / triton）连续 3 次失败。代理地址通过 **build-arg** 传入，只影响构建期网络，**没有修改 Dockerfile 的任何业务步骤**，也没有写进镜像 label。这是环境绕行，不是代码改动。

为什么没用 `--pull`：`registry-1.docker.io` 直连超时（`docker/dockerfile:1.7` 前置镜像拉不到），而本机已有 `python:3.11-slim` 与 `node:22-alpine` 基础镜像。**如实记录：本轮未执行 `--pull`**。

## 7. 这轮可以怎么写 / 不能怎么写

**可以写**（都有产物与分母）：

- 上传归属一致性：非法 metadata / 提交失败 / ACL seal 失败三个场景都有明确结果，且**无幽灵 owner、无上传者失明**（11 条测试 + 容器内实测）。
- 权限语义保持：只读 ACL 成员不能 activate/delete/retry；同名 source URI 不被他人覆盖；删除后历史作业不重新暴露；隐藏项不消耗分页配额。
- 评测快照边界：store 为空或文档集合变化时不再复用旧阈值（实测 4 条硬差异）；损坏 store 给明确失败而非未初始化变量异常。
- 镜像可追溯：**仓库原始 Dockerfile** 构建成功，`org.opencontainers.image.revision` 与构建时 commit 一致，CI 里有可执行的比对步骤。
- 部署事实：四服务 healthy；401/401/200；liveness 与 RAG readiness、MCP capability 分开记录，MCP 未加载时如实 `degraded`。

**不能写**：

- 「`--pull --no-cache` 构建通过」——`--pull` 未执行（registry 直连失败），只做了 `--no-cache`。
- 「CI 镜像构建通过」——GitHub runner 上从未跑过。
- 「支持多用户账号体系」——单 API Key + 文档级 ACL。
- 「SSH 已联调」「真实断线恢复」「GPU 版已换 CPU torch」——都没有。
- 「本地模型 vs 多智能体准确率 X%」——P2 未执行，且三层指标不合成。
- 任何「问答准确率」——Recall / 门控权衡 / 引用支持 / judge / 确定性覆盖各自分母。
