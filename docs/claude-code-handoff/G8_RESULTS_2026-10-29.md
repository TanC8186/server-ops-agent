## 2. 修复的缺陷（全部有实测复现，不是推断）

### 2.1 【P0】构建上下文凭据排除只覆盖根目录，真实私钥进了镜像

`.dockerignore` 里裸写 `*.pem` / `*.key` / `.env*` / `__pycache__/`。
Docker 的 `.dockerignore` 用 `filepath.Match` 语义，`*` **不跨 `/`**，所以这些
模式只匹配构建上下文根层。

实测（不是推理）：用一个探针镜像在容器内 `ls -R` 打印构建上下文的实际内容，
`a/nested.pem`、`a/b/deep.key`、`a/.env.local`、`a/b/__pycache__/` 全部进了镜像。
对真实镜像的检查：

```
/app/servers/AgentTest.pem   755  1674 B
sha256(宿主 servers/AgentTest.pem) == sha256(镜像内该文件)  → 29e56188ab88…
```

`servers/AgentTest.pem` 是一份**未加密的 2048-bit RSA 私钥**。

修法：全部敏感模式加 `**/` 前缀，并补 `**/*.ppk` / `**/id_rsa*` /
`**/id_ed25519*` / `**/*.p12` / `**/*.pfx`。重建后的镜像验证：

```
find /app -name "*.pem"  →  只剩 .venv 里的 certifi/grpc CA 证书
find /app -name "*.pyc"（排除 site-packages）  →  0
ls /app/.env*  →  只有 .env.example
```

G7 结果文档 §`docker build` 上下文仿真里写的"`servers/AgentTest.pem` EXCLUDED"
**是错的**，本提交已在 G8 文档中更正，不再沿用该结论。

### 2.2 【P0】cloud_multi 约 1/3 概率直接失败：模型把 JSON Schema 当答案抄回来

同一 prompt 连跑 8 次，3 次输出的顶层键是 `$defs` / `properties` / `required` /
`type`，业务字段 `assignments` 一个字没有——模型把 prompt 里嵌的
`Model.model_json_schema()` 文档本身当成了答案。

旧实现把它当普通 `ValidationError`，重试指令说"上一次输出不是完整合法的 JSON，
请只输出 JSON 对象本身"——模型于是继续抄同一份 schema，两次尝试全军覆没。

修法：新增 `_looks_like_schema_echo()` 识别该形态（要求命中 ≥2 个 schema 定义
关键字**且**缺业务顶层字段，避免误判合法实例），并给专门的纠正指令，明确点名
`$defs` / `properties` / `required` 与"要数据实例，不要输出 schema"。

实测：修复前 5/8 成功 → 修复后 8/8。基准里这一项从 1 次硬失败变为 0 次。

### 2.3 【P0】`docker compose up --force-recreate` 从不采用新构建的镜像

`docker-compose.yml` 的 `app:` 只有 `build:`、没有 `image:`，compose 把镜像名
推导成 `on_call_agent-app:latest`，于是"重建"实际是复用本地同名镜像，新构建的
`oncall-agent:g8-final` 根本不会被使用。这是仓库自己注释里警告过的"陈旧镜像
陷阱"在 compose 层的具体形态。

修法：加 `image: ${APP_IMAGE:-on_call_agent-app:latest}`。默认值不变（不改变本地
开发习惯），验收时可钉死：

```
APP_IMAGE=oncall-agent@sha256:<digest> docker compose up -d --force-recreate app
```

本轮验收即用 `APP_IMAGE=oncall-agent:g8-final`，容器 `.Image` 已核对等于上面
那个 digest。

### 2.4 【P0】评测 gold 用了在唯一真实服务上永远执行不了的工具

`search_log` 需要 `topic_id`，而 `services.json` 里唯一目标 `agent-test-server`
没有声明任何 topic；`bind_tool_args` 在 `target.topics` 为空时会**拒绝**任何显式
topic 参数（这是防越权的正确设计）。4/5 个评测场景却把 `search_log` 当 gold。

实测：`bind_tool_args({"topic_id": "topic-001", ...}, Target(topics=()))` →
`ValueError: 目标 agent-test-server 未声明日志主题，拒绝按 topic_id=topic-001 读取日志`。

修法：改用生产实际在用、按服务名自动解析 topic 的 `search_service_logs`。
`validate_eval.py` 只校验工具名存在于注册表，抓不到"存在但永远跑不通"。

### 2.5 其余

## 3. 双模式同题对比（本轮核心）

### 3.1 题集

`eval/mode_benchmark/tasks.jsonl`，**18 条**，覆盖 14 个桶：

| 桶 | 条数 | 桶 | 条数 |
|---|---:|---|---:|
| cpu | 2 | knowledge | 1 |
| memory | 2 | knowledge_no_answer | 1 |
| disk | 2 | target_ambiguous | 1 |
| network | 1 | target_unclear | 1 |
| service_anomaly | 1 | healthy_control | 1 |
| logs | 2 | param_boundary | 1 |
| negation | 1 | unauthorized_tool | 1 |

sha256：`89b54d102ca79092e5ec1361d7e6949ce307b31f89701c8bb77bf14854cc2586`

指纹写死在 `scripts/mode_benchmark.py` 的 `TASKS_SHA256`。改题集必须同步改常量，
否则脚本拒绝运行——本轮实际触发过一次（改了 MB-13 后旧常量导致云端那次运行在
结束时被拒绝写结论），这正是它该有的行为。

### 3.2 运行条件

- 同一份题集、同一服务目标、同一 MCP 工具目录、同一只读工具白名单
  （`READ_ONLY_TOOLS`）、同一 SSE 解析与计分。
- 本地：`Qwen2.5-1.5B-Instruct` LoRA SFT → SignRound AWQ 4-bit
  （`training/out/qwen15-v9-signround`，`quant_method=awq`, `bits=4`,
  `group_size=128`, `sym=true`），WSL vLLM 0.32.0 起在 `:8001`，
  容器经 `host.docker.internal:8001` 访问。
- 云端：`cloud_multi`，Supervisor + metrics/logs 专科 + Reviewer。
- 并发 1，任务间隔 2 s，单任务超时 300 s。

### 3.3 结果

| 指标 | local（QLoRA 4-bit） | cloud_multi |
|---|---:|---:|
| 任务数（分母） | 18 | 18 |
| 正常结束 complete | **18** | **18** |
| 报错结束 error | 0 | 0 |
| 端到端延迟 p50 | **3.768 s** | 17.889 s |
| 端到端延迟 p95 | **6.189 s** | 39.008 s |
| 端到端延迟 mean | **4.071 s** | 20.849 s |
| 单任务输入 token 均值 | **1 047.8** | 5 964.1 |
| 单任务输出 token 均值 | **231.3** | 1 338.9 |
| 工具调用成功率 | **0.355** | 0.279 |
| 计划工具召回 | 0.875 | **1.000** |
| 计划工具 F1 | **0.533** | 0.160 |
| 目标绑定的发现调用（16 个任务要求） | 16/16 | 16/16 |

**必须一起看的两个数**：本地召回 0.875 但 F1 0.533 → 计划更"省"，会漏工具；
云端召回 1.000 但 F1 0.160 → 几乎把整本工具目录都规划进去，覆盖全但极不精确。
这不是"谁更准"的问题，是两种规划风格：本地是单次结构化输出、云端是
Supervisor 分派给两个专科后各自铺开。

**工具调用成功率两边都低（0.355 / 0.279），原因不在代码**：真实腾讯云侧返回
`account is abnormal（CLS service is unregistered）`、`namespace(QCE/APP) or
metricName(cpu_usage) invalid`、`unauthorized operation or the instance has been
destroyed`。这些是账户/资源状态问题，两条链路都会遇到，因此不能用它比较模型优劣。

### 3.4 可以写 / 不能写

**可以写：**

- 在固定 18 条运维任务上，本地 Planner 的端到端延迟 p50/p95 分别是 3.8 s / 6.2 s，
  cloud_multi 是 17.9 s / 39.0 s。
- 本地 Planner 单任务输入/输出 token 均值为 1048 / 231，云端为 5964 / 1339。
- 本地模式在无云凭证时可独立运行；计划不合法时**明确停止**，不调用在线模型
  （`allow_cloud_fallback=False`，代码与测试双锁定）。
- 云端模式使用 Supervisor + metrics/logs 专科 + Reviewer 的多智能体编排，
  18 次运行全部产生角色阶段事件。
- 云端规划召回更高（1.000 vs 0.875），本地规划更精确（F1 0.533 vs 0.160）。

**不能写：**

- "本地模型准确率 X%" / "多智能体准确率 X%"——上表所有比率的分母都是**固定 18 条
  任务**，且两条链路工具集与拒答语义不同，不是一个可比的"准确率"。
- "本地模型全面优于云端"——召回是云端更高。
- "4-bit 无损"——本轮没有重跑 fp16 与 4-bit 的同题对照，`training/RESULTS.md`
  里的旧数字不能当本轮证据。
- 把工具调用成功率当成模型能力——两边都被云账户状态压低了。
